## 6. Two structural problems with the PRD as a status document

1. **Requirement and status are mixed in one section.** §11 Fase 2 now carries an inline "Status audit (2026-09-26)" block, and Tasks 2.12/2.15/2.16/2.18/2.19 each carry hand-written status prose. The block is **already stale**: it says `/owner-dashboard/customers` does not exist, and in the working tree it exists as an untracked stub. A hand-maintained status inside a requirements document cannot stay true.
2. **The PRD's own checklist is not trustworthy as evidence.** Every task in §11 is still `- [ ]` unchecked, including 0.1 (monorepo) and 2.5 (Frame Studio), both of which are demonstrably built. So the checkbox state is not a completion signal in either direction. This matrix replaces it with an evidence-linked status per task.

**Recommendation (direction only):** separate §11 into _requirements_ (stable) and a _generated status report_ (regenerated by a script from the evidence in this audit), and mark each ADR that a requirement supersedes rather than editing the requirement text in place — the failure pattern visible in PC-01, PC-12, and PC-13.
