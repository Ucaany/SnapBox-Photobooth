# Task 0.5 Firebase Setup: Implementation Plan

PRD line 1970: "Firebase project, Email/Password auth enabled, Admin SDK credential generated, custom claims schema documented."

## Goal

Wire Firebase as SnapBox identity provider (PRD 10.3): a reusable auth package, Admin SDK init from env, a documented custom-claims contract, and a local guard that the claims stay in sync. No business features (no login page, no provisioning) — that is Phase 1.

## Prior art already in repo (do not duplicate)

- `packages/shared/src/env.ts:40` already validates `FIREBASE_ADMIN_PROJECT_ID`, `FIREBASE_ADMIN_CLIENT_EMAIL`, `FIREBASE_ADMIN_PRIVATE_KEY`, and the four `NEXT_PUBLIC_FIREBASE_*` client vars.
- `.env.example` already lists all Firebase vars (PRD 10.14). No new env vars needed.
- `supabase/config.toml:97` already has `[auth.third_party.firebase]`; `scripts/check-firebase-project-id.mjs` already guards project-id consistency (`pnpm check:firebase-project-id`).
- `packages/shared/src/auth.ts:86` already has `customClaimsSchema`, `sessionSchema`, and `ROLE_PERMISSIONS`.
- No Firebase SDK code exists anywhere yet.

## Resolved decisions

1. **Claim contract**: emit **two** claims. `role` = Postgres role string for Supabase (`authenticated`); `app_role` = application role (`CEO` | `OWNER` | `STAFF`); plus `tenant_id` and `parent_tenant_id` (null for CEO). App code reads `app_role`. Supabase overrides `role` and `app_metadata.role` is unreachable for third-party Firebase tokens, so `role` must carry the Postgres role.
2. **Package**: new `packages/auth` wrapping both `firebase-admin` (server) and `firebase` (browser client). Web now, kiosk/CLI later.
3. **Credential**: three existing env vars via `cert({ projectId, clientEmail, privateKey })`. Normalize literal `\n` in the private key. No JSON file.
4. **Docs**: `docs/ADR-003-firebase-auth.md` (ADR-002 format), plus Task 0.5 row in `docs/PHASE-0.md` and README.

### 2. `packages/auth/src/claims.ts` — canonical claim contract

Single place that defines and builds claims. Types derive from `@snapbox/shared`, never re-declared.

- `SUPABASE_POSTGRES_ROLE = 'authenticated'` constant with a comment explaining why (Supabase picks the Postgres role from the `role` claim; app role cannot live there).
- `buildCustomClaims(input)` returning `{ role: 'authenticated', app_role, tenant_id, parent_tenant_id }`, validating `app_role` via `userRoleSchema` from shared. Enforce invariants: `CEO` → both tenant ids null; `OWNER`/`STAFF` → `tenant_id` non-null; `STAFF` → `parent_tenant_id` non-null.
- `firebaseClaimsSchema` (Zod) validating the _shape as stored in the token_ (snake_case `app_role`, `tenant_id`, `parent_tenant_id` plus `role`). Distinct from `customClaimsSchema` in shared (which is camelCase and currently lacks `app_role`).
- `toCustomClaims(decoded)` mapping token claims → `CustomClaims` for app code, so the wire/storage split is explicit.

### 3. Update `packages/shared/src/auth.ts`

Extend `customClaimsSchema` (line 86) to add `appRole: userRoleSchema` and make `role` the Postgres role (keep `tenantId`/`parentTenantId`). `Session` stays app-facing (uses `appRole`). Add a comment referencing ADR-003. Keep `hasPermission`/`canAccessTenant` reading `session.role` — decide there whether `Session.role` stays the app role name (recommended: yes, `Session` is app-domain and unaffected by the Postgres `role`). Do not break existing consumers; grep first.

### 4. `packages/auth/src/admin.ts` — server-only Admin SDK init

- `getFirebaseAdmin()`: lazy singleton stored on `globalThis` (same pattern as `packages/db/src/client.ts:34` to survive Next dev reloads). `initializeApp({ credential: cert({ projectId, clientEmail, privateKey }) }, 'snapbox-admin')`, `privateKey.replace(/\\n/g, '\n')`.
- Validate via `serverEnvSchema` from `@snapbox/shared/env`; throw a clear message on missing config (mirror the `DATABASE_URL` error style at `client.ts:43`).
- Export helpers used by Phase 1 but keep them thin: `verifyIdToken`, `setUserClaims(uid, claims)`, `createUserWithoutPassword`, `setUserDisabled`. Do not build the provisioning flow here.
- Add file-top comment: server-only, never import from client components.

### 5. `packages/auth/src/client.ts` — browser client SDK init

- `getFirebaseClient()` initializing from `NEXT_PUBLIC_FIREBASE_*` via `publicEnvSchema`; singleton guard; export `getFirebaseAuth()`.
- Guard so importing `client.ts` in a server-only context fails loudly if misused.

### 6. `packages/auth/src/index.ts` barrel

## Failure modes to handle

- Missing/invalid Admin env → clear throw at init, not at first request.
- Private key with literal `\n` → normalized.
- Claims builder rejects `OWNER` without `tenant_id`, `STAFF` without `parent_tenant_id`, `CEO` with tenant ids.
- Client bundle accidentally importing `admin` → architecture guard (barrel excludes it).

## Out of scope (deliberately)

- Firebase console project creation, Email/Password toggle, and generating the real service-account key: manual console actions outside the repo. Document the exact console steps in ADR-003 and README; the code only consumes the credentials.
- Firebase blocking functions (identity platform) deployment — needs a paid plan; document the required claim shape, implement in a later phase.
- Login page, middleware, provisioning, staff invite (Phase 1).
- Sentry/Vercel/Cloudflare (Task 0.6).
