# Task 1.1 Landing Page Plan

## Context and decisions

- Replace the current internal component gallery at `/` with the public SnapBox landing page. Preserve the gallery at `/gallery` so existing design-system evidence remains reachable.
- Public marketing layer uses the PRD SnapBox palette: yellow `#FFDD00`, violet `#8B5CF6`, pink `#FF1F8F`, warm white `#FFFEF5`, ink `#141414`. Do not alter shared `@snapbox/ui` or ADR-002 blue tokens.
- Use the existing Next.js App Router, `next/font` typography (Space Grotesk, Inter, JetBrains Mono), Tailwind v4, and existing `@snapbox/ui` primitives. Do not add a component library or animation dependency.
- Anti-slop applies DURING implementation. Design read: public B2B SaaS marketing site for photobooth operators, with intentional neobrutalist editorial language. Dials: ENERGY 3, RHYTHM 3, MOTION 2. Gradient is limited to the hero as the PRD identity accent. Hard borders/shadows communicate physical kiosk hardware and tactile actions.
- No verified public content exists for testimonials, tenant logos, pricing values, WhatsApp number, address/hours, camera registry, team/statistics, or installer URLs. Ship explicit placeholders only (`[REAL DATA]`, `Coming soon`) and never fabricate names, numbers, claims, or links. WhatsApp CTA reads `NEXT_PUBLIC_SALES_WHATSAPP`; when absent it renders a visibly disabled/labelled state, not a dead link.
- Contact submission backend, Resend, Turnstile, Firebase, and real download releases are outside available foundations. Keep contact/download surfaces functional as honest states and wire only to existing real endpoints/env when available; do not invent API contracts.

## Interaction and content rules

- Header links must point to implemented routes. Mobile menu button has `aria-expanded`, `aria-controls`, visible focus, Escape close, and body-safe layout.
- Accordion buttons use `aria-expanded` and `aria-controls`; Enter/Space work through native buttons; panels preserve readable focus order.
- Every CTA has a real destination or a visibly labelled unavailable state. No generic `Learn More`, `Get Started`, or dead buttons.
- Contact form must not imply delivery if no server action exists. Use a disabled/pending state with a clear label, or wire a real existing endpoint only after validating its contract.
- Use no testimonial section as social proof until verified attribution is supplied. Render a pending placeholder instead of fictional quotes.
- Avoid fake statistics, fake camera counts, fake plan prices/features, fake logos, fake downloads, fake address/hours, fake security/performance claims.
- Use one marquee maximum. Pause or disable animation under reduced motion and provide accessible static text/labels.

## Validation

1. Run `pnpm --filter @snapbox/web lint`, `pnpm --filter @snapbox/web typecheck`, and `pnpm --filter @snapbox/web build`; run token-sync check if shared token files are touched.
2. Inspect every public route at desktop and mobile widths. Confirm no horizontal overflow, hero CTA visible, nav stays usable, 44px targets, focus indicators, contrast, and gradient text readability.
3. Click-through record: desktop/mobile menu opens/closes and Escape works; every header/footer link resolves; WhatsApp CTA opens only with valid env and disabled state without env; FAQ expands/collapses; unavailable form/download controls communicate state; no console errors.
4. Inspect generated HTML/metadata for title, description, canonical, OG, `id-ID`, Organization/Product/SoftwareApplication/FAQPage JSON-LD, sitemap XML, and robots rules.
5. Run an anti-slop delivery gate: no em dash in visible copy, fabricated content, ghost links, dead controls, generic FAQ, unsupported claims, or unreasoned gradient/animation; document the design-read dials and reasons in the implementation summary.
